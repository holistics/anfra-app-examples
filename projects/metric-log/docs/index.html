Know why a metric changed.

In Anfra a metric is defined once and every chart that asks for it gets that definition. That is the promise, and it also means one edit moves every chart at once, unseen. anfra-metric-log turns an edit into a reviewed request: who asked, which numbers move, who approved, why.

This is a concept, built for the 2026 Anfra App Competition.
  • There is no sign-in. A “Viewing as” switcher stands in for it.
  • The AI drafts are simulated: prepared answers for three sentences.
  • Slack is shown in Settings and sends nothing.
  • The live demo shares one writable repo. Anyone’s approval changes it for everyone, and a restart resets it.

The session it plays

  1. Lily (finance) writes: “Revenue shouldn't include refunded orders.”
  2. Mark (analyst) opens it, finds a drafted definition, edits it, gives a reason, and submits. It is checked to compile first.
  3. Hannah (data lead) sees old and new definitions side by side, net_revenue, gross_margin and aov as affected, and the charts that query them, with the numbers computed by Anfra under both definitions.
  4. She approves. The dataset file is rewritten and committed with the request, requester, editor, approver and reason in the message.
  5. Later, Lily adds a decision to the metric's history, with Hannah and the data team. It saves the value for its dates and the definition that was live.

What you see

The home is the metric tree, drawn from the dataset files, on a canvas. Each card shows a metric's value for the chosen date range and a small trend. Click a card and the side panel opens on that metric: a chart you can switch between area, column and table, a Breakdown by order date or by a field such as channel or category, then tabs for its History, Comments and Requests. Click the card again, or an empty part of the canvas, to go back to your inbox.

The date range at the top left works like the one in Holistics: presets such as Last 7 days or Month to date, or pick any two days on the calendar. It opens on Year to date. The chart steps by day, week or month depending on the range, and every number compares with the period just before it.

When a repo has more than one dataset, a dataset dropdown appears and the canvas shows one dataset’s metrics at a time, each with its own date field. The moon/sun button at the top right switches between light and dark mode. It follows your system until you choose, then remembers your choice.

History, with the people in it

Every metric keeps a short history: applied changes, events (Black Friday, an outage), decisions (cut the discount to 15%) and learnings (the smaller discount is the likely cause). Each entry shows its dates, the value Anfra computed for them, and who was involved: a face for each person, a lettered circle in the team's colour for each team, stacked when several were. A learning can say which entry it follows. “Relevant” also shows entries logged on the metrics this one is built from.

How it works

browser → anfra-metric-log   pages, requests, impact, approve, commit
              │
              └→ anfra serve (127.0.0.1)  → your data
repo files:  datasets/*.aml   apps/**/*.html   metric-log/  (requests, log, timeline)

It reads every dataset file for metrics and every app for the queries that use them, so the list of affected charts is derived, never typed. To get the new numbers it queries a temporary copy of the dataset with the new definition. The live file is written only on approval.

Config

version: 1
anfra:
  repo: ./demo
  url: http://127.0.0.1:7899
people:
  - { id: lily,  name: Lily,  team: finance, role: stakeholder }
  - { id: mark, name: Mark, team: data,    role: analyst }
  - { id: hannah, name: Hannah, team: data,    role: lead }
defaults:                      # for every metric without its own entry below
  owner: team:data
  approval:
    - { stage: review, any_of: [role:lead] }
metrics:
  sales.revenue:               # only the exceptions need an entry
    owner: team:finance
canvas:
  date:
    sales: shop_orders.order_date   # the date each dataset is trended and filtered by
notifications:
  slack: { enabled: false }

The demo also lists simulated_drafts, the three prepared sentences. Leave it out on your own repo.

Run it

git clone https://github.com/holistics/anfra-metric-log
cd anfra-metric-log
npm install
npx anfra-metric-log check    # config matches the repo, owners and approvers exist
npx anfra-metric-log serve    # starts anfra serve if needed, then http://127.0.0.1:7900

Needs the anfra CLI and Node 20+. The demo is a small shop: orders, refunds and costs in DuckDB, six metrics, two charts.

Use it on your own Anfra repo

It needs nothing in your repo's apps. It reads datasets/*.aml, runs next to anfra serve, and writes only on approval.

  1. Clone holistics/anfra-metric-log (private: Holistics org members only) and run npm install.
  2. Copy anfra-metric-log.yml. Set anfra.repo to your repo's folder (it must be a git repository) and anfra.url to your anfra serve. If nothing answers there, serve starts one.
  3. List your own people, and set defaults for owner and approver, so you don't have to list every metric.
  4. Set canvas.date to a date field for each dataset you want trended and filtered by date. Without it the cards show values only, and the date filter is hidden.
  5. Run check, then serve, and open http://127.0.0.1:7900.

Tried on a copy of a 172-metric repo (two datasets, DuckDB): every metric appeared with its value, a change request ran from request to approval, the dataset file was rewritten and committed, and the impact view showed the 15 metrics it moved, with real before and after numbers. Approval commits straight to the repo's current branch, so try it on a copy first.

What it does not do yet

  • Charts that build their query at run time are not found. It reads the AQL written out in an app's createQuery call. If an app assembles the query in code, the impact view lists the affected metrics but says no chart was detected. In the repo we tried, none of the 41 queries could be read this way.
  • Only dataset metric blocks are tracked, not the measures inside models.
  • A very large metric set is crowded. 172 cards load in about eight seconds and the canvas has no search or collapse yet.
  • One approval stage, one machine, and “Viewing as” instead of sign-in (see below).
  • No simulated drafts for your sentences. A request on your repo goes to the analyst, who writes the new definition.

Good to know

Today, it runs on one machine. The demo plays Lily, Mark and Hannah on one laptop, and “Viewing as” stands in for signing in. A request is a file in the repo on that machine, so on separate laptops it would not reach anyone else.

Ideally, a team shares one copy. anfra-metric-log and anfra serve run on a shared machine, behind real sign-in (for example anfra-user, which already knows who people are). Everyone opens the same link, a request lands in the right person's notifications at once, and an approval commits to a branch or opens a pull request instead of writing to main.

Where is it stored? Requests, the change log and timelines are JSON files under metric-log/, committed with the change. Not in the warehouse, and no query changes.

What if the file changed while a request was in review? Approval is refused and the request goes back for a fresh review.

Several approval stages? The config format already allows a list. This version enforces one.

Not doing: drawing a metric tree by hand, editing charts, row-level access (that is anfra-user).
