# Usage sample: who uses Pulse Gym's dashboards and metrics

A fictional 180-day log of who at Pulse Gym (the company in `samples/pulse`) opened which dashboard and queried which metric. It runs from Wed 22 Apr to Tue 20 Oct 2026 and is generated by a deterministic script. The `usage` Dataset (`datasets/usage.dataset.aml`) sits on top of it, and the Usage analytics app (`apps/usage-xray.html`) reads it.

Show this label on every page built from this folder:

> Synthetic data (Pulse Gym usage log, fictional).

Every person in it is made up. Names pair a common English first name with a common surname, and emails end in `@pulsegym.example`.

**Anfra does not record usage today.** The SDK exposes no usage data. This log is the shape such a record could take: the org's server writes one row per request, saying who, when, which dashboard or metric, and whether it was a view or a query.

## What is in it

- **People** (`users`, 40): name, email and the day they joined.
- **Assets** (`assets`, 59): 14 dashboards and 45 metrics, each with the day it was created. A dashboard has an owner (`owner_id`, a person); a metric has none.
  - A dashboard's `name` is its Data App path, as under `apps/` (`pulse-gym/studio-overview`); `label` is its title.
  - A metric's `name` is its Dataset metric name. The 33 metrics of `datasets/pulse.dataset.aml` keep their names and labels there; the other 12 belong to two datasets this repo does not have (`pulse_marketing`, `pulse_ops`).
  - Names are unique. A dashboard and a metric can share a label (Member Retention).
- **Dashboard metrics** (`dashboard_metrics`, 49): which metrics each dashboard shows.
- **Events** (`events`, 10,672): one row per request.
  - `action`: `view` (a dashboard opened, 3,372), `query` (a metric computed, 7,279) or `export` (a dashboard saved to a file, 21).
  - A query run by a dashboard carries `parent_dashboard_id` and follows that person's view of it within 5 minutes (6,770). The data team also queries metrics on their own, with no parent (509).

Times are local (Asia/Ho_Chi_Minh) without a zone.

## Definitions

- **View**: one dashboard opened.
- **Export**: one dashboard saved to a file (CSV or Excel). It has no parent.
- **Query**: one metric computed. Opening a dashboard queries each metric on it, unless anyone opened the same dashboard in the 4 hours before: the server answers from its cache then and logs no query.
- **Active person**: anyone with an event in the period.
- **Not opened in N days**: a dashboard with no view in the last N days. One never opened counts from the day it was created.
- **Now** is 20 Oct 2026, the last day of the log, not today.

## The stories in the data

Each one is planted on purpose and checked on every build.

1. **A long tail.** The top five dashboards get 81% of views; seven of the 14 have under 100 views in 180 days. Five have not been opened in the last 90 days, three of them never (Old KPI Board, Pilates Waitlist, Trainer Payroll Draft). Seven metrics are never queried.
2. **A fading scorecard.** Weekly Studio Scorecard goes from about 4 views a day before 15 Aug to about 1 after.
3. **A metric whose only dashboard went quiet.** Towel Fee Revenue sits on one dashboard, Towel & Amenity Fees, which nobody has opened since 22 Jun. Nothing has queried the metric since.
4. **People who stop coming.** Six people were active until early June or early July and not since (Liam Walker, Sophia Young, Hannah Anderson, Charlotte Campbell, Mia Moore, Daniel Evans). Two have never done anything (Nathan Jackson, Jack Wright).
5. **Quiet weekends.** A weekend day carries about a tenth of a weekday's events.
6. **An export loop.** One person (ops_1) exports Member Retention every Monday around 08:00, from 1 Jun to the end of the log: 21 exports. Nobody else exports anything.

## Checks

`db/build_duckdb.py` runs these checks on every build and writes nothing if one fails:

1. Every foreign key has its parent row, of the right asset type.
2. Names and emails are unique, emails on `pulsegym.example`; asset names are unique.
3. Actions fit their asset: people view or export a dashboard and query a metric; only queries have a parent.
4. Each query with a parent follows a view of it by the same person within 5 minutes, and the dashboard shows that metric.
5. A view logs no queries only when anyone viewed the same dashboard in the 4 hours before.
6. Every event falls in the log, on or after the day the person joined and the asset was created.
7. Totals: 3,000 to 4,000 views, 6,000 to 8,000 metric queries, and 450 to 650 views for the top dashboard.
8. One check per story above, each with the size the story needs.
9. The file is under 40 MB.

It also generates the data twice and stops if the two runs differ.

## Rebuild

Anfra reads `usage_duckdb` from `samples/usage/data/usage.duckdb` (see `.anfra/data_sources.yml.example`). After changing `db/usage_seed.py`, stop any `anfra serve` using the file, then rebuild from the repository root:

```sh
uv run --no-project --with duckdb==1.4.2 python samples/usage/db/build_duckdb.py
```

The seed is pure Python with one seeded RNG, so a rebuild with no change writes the same rows. `python3 samples/usage/db/usage_seed.py` prints row counts and a digest without building. Pin DuckDB to the version anfra bundles (1.4.2 in anfra 0.10.2), or anfra may not open the file.
